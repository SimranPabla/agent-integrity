## Technical failures: phase-specific state invariants

The task 9 instruction about no receipt/release mutation on technical failure must be read with the approved durable phase machine. It forbids unsafe or duplicate issuance, consumption and release; it is not a rollback promise across separate synchronized stores. Authentication nonce state is distinct from receipt nonce/consumption state. Tests must name which state they inspect.

| Boundary or last proven phase | Required invariant and recovery evidence |
| --- | --- |
| Closed parsing, bad MAC, or queue rejection before admission | No auth nonce, transaction, receipt or release mutation. Queue rejection precedes nonce consumption. |
| Nonce conflict | Preserve the existing auth nonce record; no downstream mutation. |
| Auth nonce consumed; reservation/snapshot/verification not yet complete | Retain the replay record and any proven request reservation/snapshot/verification state. No receipt may be issued before valid preparation; no response bytes. A same-nonce retry remains replay; a fresh-nonce retry may recover only the exact bound request. |
| receipt-prepared; signing/issuance fails or crashes | Retain original transaction, deterministic run ID/receipt nonce, signing time, frozen key registry and request/snapshot bindings. Inspect store state and complete only the same issuance; never choose replacement inputs, erase uniqueness records or issue a second receipt. Missing exact key/snapshot or contradictory evidence fails closed. |
| receipt-issued; consume result not yet proven | Preserve the issued receipt. Inspect validated shared-transaction store markers. Never infer consumption from an exception or absence of a phase-journal update, and never blindly consume again. Proven unconsumed non-PASS recheck closes the receipt and commits RELEASE_REFUSED under the existing design; ambiguous state makes readiness false. |
| Consumption succeeded before phase/result publication | Retain the consumed marker. The existing consumed-release recovery path checks store-backed bindings, fresh time, trusted inputs and exact bytes before result commit. No refund, reset, second consume, or fresh receipt. Until proof and result commit succeed, return no bytes. |
| release-refused or result-committed | Preserve the terminal outcome and request binding. Authenticated same-body retries use persisted outcomes, not a new signing/release attempt. PASS redelivery is allowed only within the original delivery/expiry window; expiry returns no bytes and never reopens the transaction. Each retry's new auth nonce is deliberately consumed. |

Record faults after publication but before the caller sees completion, including sync failures, rather than assuming a thrown exception proves no disk mutation. Require root-lease/coordinator ownership and shared transaction identity during inspection and recovery. Unknown/contradictory records keep readiness false and require the approved offline-exclusive procedure.

**Open partner clarification:** confirm that Lars intends no *unsafe additional* issuance/consumption/release after a technical failure while retaining already committed replay and recovery state. This interpretation follows the frozen design but is not yet a new agreement with Lars. Do not change the lifecycle or block starting Task 8 merely because joint wording confirmation is pending; a demonstrated incompatible requirement would require an explicit design decision before changing behavior.

4. Test-only signing/HMAC material provisioned outside committed fixtures; pinned public authority/receipt keys and signed trust-manifest generation/digest. Preserve only public/non-sensitive evidence; never publish HMAC/signing keys or private source content.
5. If the CAGE mapper consumes VEIP warrant/reliance evidence, a pinned complete post-[#438](https://github.com/google/cybernetic-agent-governance-engine/pull/438) record and mapping, including the renamed attestation time, distinct required versus declared governing versions, warrant digest and risk/issuer metadata. ### Required observable scenarios

- **PASS:** the real adapter sends the bound canonical request to `POST /v1/verify-release` over the private socket; the real sidecar snapshots and verifies evidence, signs and consumes once, and commits its result. CAGE validates the closed wrapper, request ID, signed receipt/profile, canonical verification equality, current trust/lifecycle, envelope digest and base64/digest/exact UTF-8 byte equality; ConsequenceGateway dispatches only that returned byte buffer. Compare captured output bytes, not reconstructed text.
- **REVIEW/BLOCKED:** valid signed receipts and findings are preserved in CAGE's evidence chain with no downstream bytes.
- **RELEASE_REFUSED:** a fresh release recheck refuses a prospective PASS; retain its original signed receipt and associated terminal refusal evidence, route non-admitting, and prove no downstream bytes or replacement receipt.
- **Binding and trust tampering:** mutate request ID, response bytes/digest, wrapper verification, source/decision evidence, receipt signature/profile/envelope binding, and trust-manifest signature/metadata/freshness/generation in isolated cases. The responsible boundary must reject; no downstream dispatch. Preserve expected versus observed outcomes per case.
- **Replay/retry:** reused auth nonce fails; same-body retry with fresh auth nonce redelivers byte-identical committed results only in-window, with no second receipt/consume. Different-body idempotency reuse conflicts; expired result does not reopen verification. Transport redelivery does not claim exactly-once downstream action execution.
- **Crash/technical failure:** exercise sign/consume/result-publication windows, storage failure, timeout/disconnect and malformed adapter responses. Preserve the phase invariants above; CAGE does not dispatch on a technical error or absent response. Recovery can release only after all required proof succeeds.
- **Health and partner trust:** each unusable sidecar-owned readiness prerequisite makes the sidecar non-ready (503 where HTTP is available); liveness is not substituted for readiness and no legacy health fallback admits work. Independently, missing, expired or rejected CAGE-provisioned trust manifests prevent adapter admission even when the sidecar is healthy. Do not add a sidecar readiness dependency on CAGE cache state or a separately loaded export.

For each scenario record expected and observed HTTP/transport outcome, verdict, signature/binding checks, durable issuance/consumption counts and markers, evidence-chain reference, and actual dispatched-byte count/digest. A local mock or standalone sample warrant does not satisfy the real-adapter fixture. Missing joint execution stays pending/INCONCLUSIVE; no integration-ready or production-ready claim follows from writing this specification.
